# ATT&CK v20.0 against 19.2 — AnnoCTR dev, October 2026

Does the ATT&CK v20.0 track (ADR-0087) change what the select path finds,
and is that change the taxonomy's or the system's? **Dev split only** (16
reports, 129 document-level parent techniques). ADR-0060's rule decides; the
frozen test split is not run or read for this question.

> **Re-run on 2026-10-21** with the Stage 3f cut-off salvage on both tracks
> ([addendum](#addendum-2026-10-21-re-run-with-the-3f-salvage)): +0.003 F1
> [−0.028, +0.028]. Neither run has a cut-off answer, and the default stays 19.2.

## Setup

- **Code**: `5b98a49` for every new run, from a detached worktree pinned to
  that commit.
- **Server and sampling**: vLLM `Inferact/Qwen3.8-27B-NVFP4`,
  `LLM_TEMPERATURE=0 LLM_SEED=13 LLM_PARALLELISM=1`, thinking off,
  `TTP_MODE=select`.
- **Prompt and corpus**: extraction prompt fingerprint `606528fb5beba5c6`, the
  same as the historical runs. The 48 MITRE procedure examples written from
  AnnoCTR reports are left out of retrieval (`TTP_RETRIEVAL_EXCLUDE_CITED`).

| Run | ATT&CK track | Code | What it isolates |
|---|---|---|---|
| `sel-dev-revoked-5d1bbe4` | 19.2 (shipped files) | `5d1bbe4`, 2026-10-11 | the historical reference |
| `sel-dev-a19.2-5b98a49` | 19.2, `ATTACK_RELEASE` unset | `5b98a49` | the code since `5d1bbe4`, and run-to-run noise |
| `sel-dev-a20.0-5b98a49` | 20.0, `ATTACK_RELEASE=20.0` | `5b98a49` | the ATT&CK release, alone |

The two tracks differ by ATT&CK only (ADR-0087 decision 3), with one
exception: the default track's gazetteer and curated relationships predate
19.2 (the `exceptions` of its manifest). On dev that changes nothing: the
gazetteer entities are the same on all 16 reports, and Stage 4b does not run
in an evaluation run.

- **What is the same**: the CAPEC entries, the embedding model
  (all-MiniLM-L6-v2), the domains of the revoked table and of the retrieval
  corpus (Enterprise), and the gazetteer as far as dev can tell. The 20.0 gazetteer has
  39 name variants the default track's lacks, 14 of 19.2 and 25 of 20.0. None
  occurs in the 16 reports, so Stage 2b and the Stage 3 prompt see the same
  names on both tracks.
- **What changes, Enterprise, 19.2 → 20.0** (`evaluation attack-diff`):
  - 9 new techniques (T1608.007, T1685.007, T1696 and its two
    sub-techniques, T1697, T1698, T1699, T1700);
  - 31 changed descriptions;
  - 500 more procedure examples (17,136 → 17,636, on 242 techniques);
  - nothing revoked, deprecated or renamed.

## The gold under two releases

AnnoCTR's gold was annotated against the ATT&CK of 2022. `evaluation`
maps it, and every prediction, through the `revoked-by` chains of one
release. T1562 and T1562.001, revoked for T1685 in 2026, become T1685 on
both sides. Stage 3c maps a revoked id the model writes to its replacement
(`attack_revoked.json`, run `sel-dev-revoked-5d1bbe4`).

v20.0 revokes no Enterprise technique, and its revoked table is identical to
19.2's. The mapped gold is therefore the same under both releases. Three
consequences:

- **The two runs share one gold.** A paired comparison is defined, and
  `compare --attack-release 20.0` and `--attack-release 19.2` give the same
  numbers (below).
- **A v20 id the 2022 gold cannot contain** (T1696–T1700) can only be a
  false positive here.
- **A sub-technique new in v20 can still score.** T1685.007 or T1608.007
  scores at parent level as T1685 or T1608, which the gold can hold.

## The 19.2 reference is exact

`sel-dev-a19.2-5b98a49` reproduces `sel-dev-revoked-5d1bbe4`:

- the same technique ids and the same candidate lists on all 16 reports;
- F1 0.584 both times (78 correct, 60 false positives, 51 misses);
- a paired difference of +0.000 [+0.000, +0.000];
- the same single unparseable selection.

So nothing between `5d1bbe4` and `5b98a49` moved the TTP outputs on dev. With
fixed sampling, a run of this configuration is reproducible. Any difference
in the 20.0 run comes from the ATT&CK data, directly or through what the
model is shown.

Totals: 78 → 81 correct, 60 → 56 false positives, 51 → 48 misses. The

What did not change:

### Where the difference comes from

`python -m evaluation release-effect --a sel-dev-a19.2-5b98a49 --b
sel-dev-a20.0-5b98a49 --attack-release 20.0` classes each parent technique the
two runs disagree on by what v20 changed about it. The class says what changed
in ATT&CK for that id; it does not prove that the change caused the
disagreement.

| Class | Ids | Differences | ΔTP | ΔFP | ΔFN | F1 if only this class came from 20.0 |
|---|---|---|---|---|---|---|
| `new_technique` | 0 | 0 | 0 | 0 | 0 | 0.584 |
| `new_subtechnique` | 0 | 0 | 0 | 0 | 0 | 0.584 |
| `status_changed` | 0 | 0 | 0 | 0 | 0 | 0.584 |
| `content_changed` (new description or more procedure examples) | 32 | 36 | +2 | −4 | −2 | 0.604 |
| `unchanged` (T1115, T1185, T1498, T1499, T1650) | 5 | 5 | +1 | 0 | −1 | 0.590 |

**The taxonomy effect on ids is nil on dev.** No revoked or renamed id is
involved. None of the 19 techniques new in v20 (9 Enterprise, 1 Mobile, 9 ICS)
appears in a candidate list or a prediction of the 20.0 run, on any report.
The gold is the same under both releases.

**Every difference goes through the retrieval content.** The gazetteer
entities are identical on all 16 reports. The candidate lists differ on 14,
and the technique sets on 11, all among those 14. The new descriptions and
the 500 new procedure examples move candidates within the lists the selector
sees. The selector reads a chunk's whole list at once, so a technique whose
ATT&CK entry did not change (the five `unchanged` ids) can still be selected
differently.

  positives) ;
- recall −0.018 [−0.069, +0.031] (69 → 67 correct).

About half of the observed F1 gain (0.011 of 0.025) goes with a parse failure
that moved from one report to another. The two reports are set aside after
the fact, so this split is a reading of the result, not a test.

### Verdict

ADR-0060's rule, fixed before this comparison:

1. **The interval must exclude 0** ([−0.019, +0.076]): not met, so the rule
   fails. The gain is +0.025, above the +0.02 floor.
2. **Precision must not drop by more than 0.02**: met, precision rises.
3. **The gain must exceed the run-to-run spread**: formally met, since the
   spread is 0 here, but about half of the gain goes with one moved parse
   failure.
4. **Cost must not grow by more than 25%**: met, −13% per report
   (uncontrolled).

**The default stays 19.2.** The 20.0 track is ready to select
(`ATTACK_RELEASE=20.0`). It loses nothing measurable on dev. On the 14 reports
without a parse failure, its precision is higher as a point estimate
(+0.041, interval [−0.015, +0.078]) and its recall lower (−0.018), on a
subset chosen after the fact.

What dev cannot say is whether v20's new techniques are found when a report
describes them: no dev report does. That question needs other reports (the
in-house set, or a corpus after 2025).

Separately, a selection answer that does not parse costs up to 6 correct
techniques on a report. It decides more of this comparison than the
taxonomy does. That is a system defect for its own change.

## Limits

- **Small sample.** 16 reports and 129 gold parents: a difference of a few
  techniques is noise for a bootstrap over documents.
- **A gold older than v20.** The release's new techniques can only cost
  precision here. Whether finding prompt injection or AI-enabled exfiltration
  is right needs reports that describe them: the in-house set, or a later
  corpus.
- **`content_changed` is broad.** 242 Enterprise techniques gained procedure
  examples. That class mixes a technique whose retrieval text changed with one
  whose new examples never surface.
- **One run per configuration.** That is enough here because the reference
  reproduced exactly, but vLLM batching is not guaranteed bit-stable.

### Verdict, ADR-0060's rule re-applied

1. **The interval must exclude 0, with a gain of at least +0.02**: not met.
   The interval is [−0.028, +0.028], and the gain is +0.003, one technique.
2. **Precision must not drop by more than 0.02**: met (−0.001).
3. **The gain must exceed the run-to-run spread**: not measured at this
   commit. The last measurement was 0 (`5d1bbe4` against `5b98a49`), and a
   one-technique gain says nothing either way. Rule 1 already fails.
4. **Cost must not grow by more than 25%**: met (−0.5% per report,
   uncontrolled).

**The rule fails, as before, and this measurement gives no reason to move the
default from 19.2.** What changed is the reading. The first comparison's
+0.025 is not an effect of 20.0 on dev. With no cut-off answer on either
side, the two tracks are one correct technique and one false positive apart,
and the precision lead seen on 14 reports is gone. On dev, 20.0 and 19.2
cannot be told apart.

The question left open above is unchanged. Whether v20's new techniques are
found when a report describes them needs reports that describe them: the
in-house set, or a corpus after 2025. Moving the default remains the
maintainer's decision.

`sel-dev-a19.2-01aeea6`.
