# 1.0 failure recipe

ADR-0097 item 23: the service is run on a stack, and five failures are made on
it, one at a time. Each case checks what the service did about the failure:
the data, the job, the health answer and the alert the rules file names for it.
The script is `scripts/check_failure_recipe.py`. It is a qualification step: it
runs on the candidate, against a stack that holds data you can lose.

The recipe is not in CI. It needs Docker, the models and an LLM endpoint that
the cases can reach or refuse, and it stops services. The tests of the script
(`tests/test_failure_recipe.py`) run in CI and need no Docker.

## Before you run it

- A stack from the candidate, started as [docker.md](../docker.md) describes,
  with `bootstrap` done. Its database holds nothing you need: the cases stop the
  database, fill the upload gate and restart `worker`. Use a stack you built for
  the test, or one whose data is backed up.
- Run it from WSL or a Linux shell, where the `docker` command reaches the stack.
  The script uses the standard library only.
- The API answers on loopback (`--base-url`, the default `http://127.0.0.1:8000`).
  `/metrics` answers loopback only. A client that reaches the port through
  Docker's published port arrives from the Docker network, and gets 403. Then
  export `METRICS_TOKEN` (the value in `.env`) in the shell that runs the script.
  The script sends it as a bearer and never writes it down.
- The stack runs with `AUTH_MODE=off` (the default). The script sends a bearer
  to `/metrics` only; its calls to `/api/queue/status`, `/api/jobs` and
  `/api/upload` send none. With authentication on, those routes need a
  signed-in user, so the cases cannot run (`/api/health` stays open).
- Nothing else uses the queue. The cases upload one fixture report each, and
  wait for it.

```bash
python3 scripts/check_failure_recipe.py --base-url http://127.0.0.1:8000 \
    --i-know-this-stops-services
```

The flag is required: the run stops and restarts `app`, `worker` and `postgres`.
Without it the script exits 2 before it runs a command. A base URL that is not
on loopback is refused the same way. `--compose-file` names the Compose file the cases
run `docker compose` with (default `compose.yaml` of the checkout). `--case NAME`
runs one case (repeat it for several). `--wait-s` sets how long a job may take to end (1200 by default: the
lease of 180 s, then a run). `--report-dir` sets where the report goes (default
`output/failure-recipe/<UTC time>`).

The run takes a while: the restore drill and the 10-minute disk condition are the
long parts. Expect the whole run to take longer than the sum of the cases'
waits.

## The cases

Each case restores the stack when it ends, whatever happened: `postgres`, `app`
and `worker` are recreated with the configuration of `.env`, without the
override the case used, and the script waits for `/api/health` to answer 200.

### worker-killed

The fixture report (`tests/fixtures/sample_report.txt`) is uploaded. When a
worker has taken it, the worker's container is killed. The worker is then
started again.

It proves that a report does not stay in `processing` after its worker died.
Its lease expires (`WORKER_LEASE_TIMEOUT_S`), and a worker runs it again. The
checks: the job ends in `completed`, `for_review` or `failed`; a failed job has a
reason; the job was claimed twice (`attempts`); one job exists for the upload;
`/metrics` shows no processing job and a live worker afterwards.

Alert: none checked here. `CtiparsorNoLiveWorker` needs the worker down for five
minutes after the lease. This recipe does not wait that long.

### llm-down

The worker is recreated with `LLM_PROVIDER=vllm` and `VLLM_BASE_URL=http://127.0.0.1:9`,
an address that refuses connections. The fixture report is uploaded.

It proves that a missing LLM does not lose a report. The checks: the job ends in
a terminal status; Stage 3 is recorded in the job's stage report as `failed` or
`skipped`, with a reason; the job is still there; the API answers before and
after the run.

Read the reason in the report. A `skipped` Stage 3 with a reason such as
"disabled" does not show that the endpoint was tried. The reason should name the
endpoint or the connection.

### database-down

`postgres` is stopped.

It proves that the database outage shows, and that nothing is lost. The checks:
`/api/health` answers 503; `ctiparsor_database_up` is 0; the condition of
`CtiparsorDatabaseDown` holds for its `for:` duration (one minute), on every
scrape. After `postgres` starts, `/api/health` answers 200, the jobs table holds
the same job ids as before the stop, and `ctiparsor_database_up` is 1 again.

### disk-nearly-full

`app` is recreated with `UPLOAD_MIN_FREE_MB` set one megabyte above the free
space the state directory has. An upload is tried.

It proves that a full disk stops uploads and writes nothing. The checks: the
upload gets 507 with "Insufficient Storage"; no file appears under
`/app/state/uploads`; no job row appears. Then the condition of
`CtiparsorDiskNearlyFull` is checked on `/metrics` for its `for:` duration (ten
minutes).

The alert needs a nearly full disk, not only the upload gate. The condition is
free space under 10 % of the filesystem or under 2 GiB. When the disk has more
free space than that, the alert cannot fire, so the case reports the alert as
**not checked** with the free space, and the run is not a pass. To check the
alert, run this case on a stack whose `cti-state` lives on a small filesystem
that is nearly full. Do not fill a disk of a machine that holds other data to
make the check pass.

`--disk-test-fs MOUNTPOINT` does that on a dedicated filesystem. The path must
be a mount point holding a file named `CTIPARSOR-DISK-TEST`, and be at most
8 GiB; the script refuses it otherwise, before any case runs. The state
directory must be on that filesystem: its total size on `/metrics` must match the
filesystem's within 1 %, or the case fails. The case then writes a filler file
on it until 1 GiB is free (below the alert's 2 GiB), checks the upload gate and
the alert for the `for:` duration, removes the filler, and checks that the alert
returns to false. The filler is removed on every outcome, including a failed
step. Set-up used for the run below: a 4 GiB ext4 image on a loop device, mounted
on a scratch directory, and a Docker volume bound to that mount with the Compose
project's labels (so `compose down -v` removes it). Remove the loop device and the
image when done.

### restore-drill

The backup commands of [docker.md](../docker.md#data-and-backups) run as they are
written (`stop app worker`, `pg_dump`, `tar`, `start app worker`). The two check
commands run on the new files. The restore line runs with one change: it names
an empty database the case creates, `ctiparsor_drill_<stamp>`, in place of
`ctiparsor`. The case then compares the restored jobs with the source's, row by
row, and the bundles and uploads of three files of the archive with the live
files, by sha256. The drill database and the backup files are removed at the end.

It proves that the documented backup restores. The duration of the restore line
is in the report as `restore_seconds`.

This drill does not restore the archive into a live state directory: the restore
line of the docs writes into a new project's volume, and a new project is the
job of `scripts/docker_smoke.sh --backup-restore`, which the container-image job
runs. The restore drill covers the database and the content of the archive.

## Reading the report

The run writes two files into the report directory: `report.md` for people, and
`report.json` for scripts. Both list, for each case, the status, the time, the
steps with their time from the start of the case, every check with its result
and detail, and every command the case ran. The last table of `report.md` lists
the seven alert rules and the cases that checked each one.

A case has one of four statuses:

- `passed`: every check passed.
- `failed`: a check failed. The detail says what was seen.
- `not_checked`: a check could not be read by the evaluator, and nothing failed.
  The evaluator reads the forms the rules file uses today: a metric compared with
  a number, a sum with a label selector, `absent()`, `time()` and division. A
  `delta()` over a range is not read, so `CtiparsorFailedJobsRising` is not
  checked.
- `error`: a step could not run (a command timed out, the API did not answer, a
  file was missing). The error line says which.

The run exits 0 only when every selected case passed. Any other status exits 1.

## When a case fails

| Case | First look at | Then |
|---|---|---|
| worker-killed: job still `processing` | `docker compose logs worker`, and `attempts` in the database | `WORKER_LEASE_TIMEOUT_S` and the worker's heartbeat; see *The queue and its workers* in [operations.md](../operations.md) |
| worker-killed: no duplicate, or no claim twice | The job rows (`original_filename`, `attempts`) | A second job for one upload is a bug in the queue; report it with the report directory |
| llm-down: Stage 3 missing, or no reason | The job's `stage_report` in `run_config_json` | A missing stage report means the run did not finish recording: check `docker compose logs worker` |
| database-down: health not 503, or alert not true | `docker compose logs app`, `[health] job store unreachable` | The check of the health route and of `/metrics` (`ctiparsor_database_up`) |
| database-down: jobs changed | `docker compose logs postgres`, and the restored volume | A changed job set after a database restart is data loss: stop, and restore the backup into a new project |
| disk-nearly-full: upload not refused | `UPLOAD_MIN_FREE_MB` in the app's environment | `api/disk_space.py` |
| disk-nearly-full: alert not true or not checked | The free space in the report and in *Disk* of [operations.md](../operations.md) | Not checked on a host with free disk; see above |
| restore-drill: `pg_restore` printed something | Its stderr in the report | The restore is not clean: the documented steps need an empty database |
| restore-drill: rows or files differ | The detail of the check | Stop the release: a backup that does not restore is not a backup |

A case that fails leaves its stack restored. Its report still holds the
commands run, so the run can be read without the stack.

## What the recipe does not cover

- The alerts `CtiparsorNoLiveWorker`, `CtiparsorQueueWaitTooLong`,
  `CtiparsorFailedJobsRising`, `CtiparsorBackupTooOld` and
  `CtiparsorBackupLastAttemptFailed` are not raised by these cases. The report
  says so, alert by alert.
- A restore into a new project, with its volumes and its port (the full
  restore). The smoke's `--backup-restore` does it.
- Load. No case sends many reports at once; the upload limit is ten per minute
  per address, and the cases stay under it. The load profile of the run below
  (`scripts/measure_queue_load.py`) measures queue wait and run time for ten
  reports; it is not a capacity limit.

#### Load profile

Definition, fixed before the runs: N copies of `tests/fixtures/sample_report.txt`,
each with a line of its own (`scripts/measure_queue_load.py`); submissions by
`burst` (all at once, at most 10 by the upload limit) or `interval` (one every
7 s, at least 6 s by the same limit); polls every 2 s; the profile waits for
each job to reach `completed`, `for_review` or `failed`. The worker ran without
an LLM: `LLM_PROVIDER=anthropic` with no key, so Stage 3 and its sub-stages were
skipped with "Stage 3 did not run" (`docker compose logs worker` of the run).
The Stage 3 result is therefore not in these numbers. Queue wait is the server's
`created_at` to the `updated_at` of the first poll that saw `processing`; run
time is that to the terminal `updated_at`.

Sources: `load-burst10/load.md` and `load.json`, `load-interval10/load.md`,

of `load.json`). Every run ended with 10 of 10 jobs terminal, no duplicate name

Alerts on the load runs (`load.md`, the table "Alert"): `CtiparsorQueueWaitTooLong`
was never true (the oldest queued report waited at most about 254 s, under its

configured shows it. `CtiparsorFailedJobsRising` is not checked by the evaluator.

Limits of these numbers: one host, one fixture size, ten reports; no LLM; the
upload limit allows ten reports a minute, so no queue of more than ten was built.
Queue wait includes the time the first poll took to see the claim (2 s at most).
The 2-worker run used a worker memory limit of 10g for that run only.
