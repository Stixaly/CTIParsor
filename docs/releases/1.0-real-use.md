# 1.0 real use: the freeze and the five reports

**Status: protocol, not run (2026-11-08).** This page is item 10 of
[ADR-0094](../adr/0094-what-1-0-promises.md) (decision 2, real use before 1.0).
It fills the gate `freeze_and_use` of [1.0-readiness.md](1.0-readiness.md).
No release is tagged before that gate passes.

The tests and the measurements use fixtures and gold sets. This protocol is
the only check of the journey on reports the project has not tuned against:
import, review, export, and an import into OpenCTI. Nothing in this page
asks for a result before the run.

## 1. The freeze

### The candidate

The candidate is the merge commit of the release pull request, and the image
main's CI published for it ([releasing.md](../releasing.md#cutting-a-release),
steps 4 and 5). Record in the readiness record:

- `candidate.git_commit`: the merge commit;
- `candidate.image_digest`: the digest of `ghcr.io/stixaly/ctiparsor:sha-<commit>`,
  the image `container-image` tested and `publish-image` read back;
- `candidate.contract_revision`: the `contract/` snapshot that passed on that commit.

Pin the install to the digest, as [upgrading.md](../upgrading.md) writes it:
`CTI_IMAGE=ghcr.io/stixaly/ctiparsor@sha256:<digest>` in `.env`. After the
start, the app container's image must report the same digest as the record
(`docker inspect --format '{{.Image}}' <app container>`). A tag alone is not
enough: `latest` and `0.x.y` move.

### Sign-in

With `AUTH_MODE` set to `local`, `oidc` or `both`, every operation of the
steps below needs a signed-in user or a bearer token ([api-permissions.md](../api-permissions.md)).
Import, review and finalize need the `analyst` role; reading a job, its bundle
or the queue needs `reader`. Either:

- run the stack with `AUTH_MODE=off` (the default), on loopback (`CTI_BIND`
  left at 127.0.0.1); or
- sign in as an analyst in the web UI, or create a token on the Account page
  while signed in as an analyst. The scripts read the token from
  `CTIPARSOR_TOKEN` (`scripts/check_model_journey.py`) and send it as
  `Authorization: Bearer ctp_…`.

Record which of the two the run uses in the private log, and keep it in the
frozen `.env`.

### What does not change during the use

| Item | Why it is frozen |
|---|---|
| The image digest | It is the candidate. |
| Every key of `.env`, including `LLM_PROVIDER`, `LLM_TEMPERATURE`, `LLM_SEED`, `ANTHROPIC_MODEL` and `VISION_PROVIDER` | The run measures one configuration. |
| The models and the corpora in `cti-cache`, and the ATT&CK release | No model download and no corpus sync during the run. |
| The policy and the thresholds saved in the app (Policy and Settings pages) | They change what the pipeline and the auto-accept do. |
| The database | The candidate migrates it once. No restore onto another image during the run. |

The analyst's own work (accepting, rejecting, editing relationships) is not a
configuration change. It is the work the run measures.

### What cancels the freeze

- A blocking incident (section 5).
- A change to any frozen item above, on purpose or by accident. The record
  says what changed; the run restarts (section 5).
- A new image for any reason.

Not a cancellation:

- a defect that is not blocking (the order of fixes follows
  [support-policy.md](../support-policy.md#release-blockers): logged, fixed later);
- a commit on `main` that does not change the candidate's image;
- a change to the documentation.

## 2. The five reports

Choose the five before the first import. Write the choice, with the cutoff
date used for "recent", in the private log (section 4), not in this page.
Fix the cutoff date before the pick, so that it is not moved to fit a report.

### Exclusions, checked

- **Not in AnnoCTR.** Compare each candidate with the documents that
  `evaluation/annoctr.py` loads: the title, and the text. A copy of a report
  published at another address is the same report.
- **Not in `data/eval/inhouse/`.** Compare the sha256 of the source file with
  the source hashes in the private manifest, `data/eval/inhouse/manifest.json`
  (its reference is in [1.0-readiness.md](1.0-readiness.md), `private_manifest_reference`).
  Then compare the family and the title. Two reports of one family count as
  one: the two GREYVIBE reports are one family.
- **Not already read by the maintainer for tuning.** A report that was used to
  write a rule or a prompt is not one of the five.

### Choice

- **Recent:** published after the cutoff date.
- **Five sources:** no two reports from the same publisher or the same
  publication series.
- **The mix** (the protocol needs these four cases, which the corpus does not
  cover):
  - one report in **French**;
  - one **fully scanned PDF** (the OCR path);
  - one imported **by URL** (the URL option of the ingest form, which calls
    `POST /api/ingest/url`). At least one.
  - the other reports: any input the interface takes (a text PDF, pasted text,
    DOCX, HTML or Markdown). Not a second copy of the same input.

  One report may cover two cases, for example a French report by URL.

French and OCR are experimental in 1.0 ([support-policy.md](../support-policy.md#what-10-promises)).
A problem on them is recorded like any other. It blocks the release only when
it is one of the four blocking classes.

### A fix during the run

A fix made because of one of the five reports is a new candidate. The report
is run again on it (section 5). A report that is not yet run may not be used
as the test of a fix made for another one.

## 3. The steps for each report

Record the time and the step for each action.

1. **Import.** Upload the file, paste the text, or submit the URL (the analyst
   role when authentication is on; see [Sign-in](#sign-in) in section 1).
   - For a URL, a refusal by the URL policy (400) and an unreachable address
     (502) are results of the input, not incidents. Note them, then choose
     another URL. A blank render of a reachable page is an incident.
2. **Follow the job.** Watch the five stages on the progress bar. At the end,
   read the job's stage report (ADR-0059): one entry per stage, with `stage`,
   `status` and `reason`. A stage that the configuration enables and that did
   not run or failed is an incident. A stage the configuration turned off is
   not, and its `reason` says so.
3. **Review** (Review page). Decide every entity and relationship:
   - accept or reject each one;
   - check the auto-accepted entities too (confidence at least 90 %, ADR-0058):
     the worker accepts them without an analyst's click;
   - decide the held items (ADR-0082);
   - add or edit relationships where the analyst needs it.

   Then reload the page. Every decision must still be there. A decision that
   is lost is blocking class 2 (section 5).
4. **Finalize.** Press `F`, or Finalize, or `POST /api/jobs/{id}/finalize`.
   Check on the Graph page that rejected objects are absent and accepted ones
   present. A Stage 5 refusal shows there, with its first errors.
5. **Export.** Download the bundle from the Graph page, or fetch it with
   `curl -D headers.txt -o bundle.json <base URL>/api/jobs/<id>/bundle` (with authentication on, add `-H "Authorization: Bearer ctp_…"`). Record
   the sha256 of `bundle.json` and the value of `X-Bundle-Validation`.
   - `validated` is expected.
   - `unverified` means the JSON schemas were missing from the image. On the
     candidate that is an incident.
   - `unknown` means the bundle was built before the verdict was stored. On a
     new report that is an incident.
   - `409` means Stage 5 refused the bundle. The bundle must not be served.
     Read the first errors, then decide whether the refusal is right. A valid
     bundle that is refused is an incident. A bundle that is served while it
     was refused is blocking class 3.
6. **Import into OpenCTI.** Use the test stack and the pycti environment of
   [TESTING.md](../../TESTING.md), section *OpenCTI import (A4)*: OpenCTI
   7.260930.0 from `docker/opencti-test/compose.yaml`, its own virtual
   environment. Import the bundle with `scripts/opencti_import_bundle.py`
   (TESTING.md, *Any bundle*): it takes the bundle's inventory, imports it,
   reads the platform back, imports it a second time, and runs the checks of
   step 7 on both readings. Its report,
   `output/opencti-import/<UTC time>/report.md`, lists each check as pass, fail
   or not_checked, with the bundle's sha256, the OpenCTI and pycti versions and,
   when `--image-digest` is given, the image digest. Exit 0 means every check
   passed.
7. **Check what OpenCTI shows.** Record each check as yes or no, with a count:
   - nothing refused on import; the import repeated a second time adds nothing;
   - one Report, named after the report, with its description and the attached
     file (`x_opencti_files`) once;
   - each object of the bundle once, on an OpenCTI object of its own: no
     duplicate by name, value or alias;
   - each relationship joins the objects the bundle names;
   - the TLP and PAP markings, the author (`created_by_ref`) and the confidence
     as the bundle set them;
   - the readings of the platform settle (two readings in a row agree).

   The script of step 6 runs these checks, from `scripts/opencti_expectations.py`,
   on this bundle. The record copies its results: a check that is `not_checked`
   is not a yes. A failed check on a bundle that Stage 5 validated is an incident
   of blocking class 4 until the record classifies it.

The candidate check of [releasing.md, step 4](../releasing.md#cutting-a-release)
(`scripts/check_opencti_candidate.sh`) is a separate release step, run before
the tag. It is not one of the five reports.

## 4. What is noted

One fiche per report. The fiches stay private, in
`output/freeze-and-use/<first 12 characters of the digest>/`. The `output/`
directory is git-ignored. The fiches name the sources and may hold content of
real reports, which may carry sharing limits. They do not go into the
repository.

```yaml
report: 1                      # 1 to 5, in the order used
date: 2026-MM-DDTHH:MMZ        # import, and finalize
candidate_digest: sha256:...
source:
  publisher: ...               # kept in the private fiche only
  kind: file | paste | url
  language: en | fr | ...
  scanned: false | true
  sha256: ...                  # of the source file, or of the URL's archived PDF
size:
  bytes: ...
  pages: ...
duration:
  import_to_completed: ...
  finalize_to_download: ...
stage_report:                  # one line per stage: stage, status, reason
  - "1: ... ; ..."
llm:
  provider: ...
  model: ...
  figures_read: true | false   # VISION_PROVIDER at its default
decisions:
  accepted: 0
  rejected: 0
  auto_accepted_checked: 0
  held_decided: 0
  relationships_edited_or_added: 0
verdict:
  x_bundle_validation: validated | unverified | unknown | refused-409
  bundle_sha256: ...
opencti:
  checks_yes: 0
  checks_no: 0
  warnings: 0
  second_import_added: 0
incidents:                     # one entry per incident
  - what: ...
    reproduction: ...
    blocking_class: none | 1 | 2 | 3 | 4
    reason: ...                # the maintainer's classification, in one sentence
```

The public part of the record holds aggregates only: the five dates, the
candidate digest, the counts of decisions, verdicts and OpenCTI checks, and the
number of incidents by class. It names no report and no publisher, and it
holds no report content.

## 5. The exit rule

The gate `freeze_and_use` passes when all of these hold:

- the five reports are run on the frozen candidate, each to the end of
  section 3, step 7;
- each has a fiche with every field of section 4;
- no blocking incident is open: each incident of a blocking class is fixed on
  `main` and run again, or the maintainer records in the fiche why it is not a
  defect;
- each report's OpenCTI checks hold, or their failure is classified in its fiche.

The four blocking classes are the release blockers of
[support-policy.md](../support-policy.md#release-blockers):

1. data loss in an upgrade, a restore or normal operation;
2. a lost review decision;
3. an invalid export presented as validated;
4. an essential journey that cannot be completed: import, review or export.

Two rules apply on top of the list:

- A bundle that Stage 5 validated and that OpenCTI refuses is blocking class 4
  until the record classifies it.
- A French or a scanned report is covered by the four classes as any report
  is. Its experimental status does not make a failure non-blocking when it
  loses data or a decision.

### If a blocking incident appears

1. Stop the run on this candidate. Record the incident in the fiche of the
   report where it happened, with its reproduction.
2. Non-blocking incidents go in the log. They do not stop the run.
3. Fix the cause on `main` by a pull request. Add a test that reproduces the
   incident and fails before the fix.
4. Cut a new candidate through the release pull request
   ([releasing.md](../releasing.md#cutting-a-release)). It has a new merge
   commit and a new image digest. Update the candidate fields of the readiness
   record.
5. Run again all five reports on the new candidate, including the report that
   showed the incident. The five fiches of the old candidate stay in the log as
   history. They are not counted.
6. Restart the freeze date in the record.

An incident in the environment, not in the candidate (Docker, the host, the
OpenCTI stack), does not change the candidate. Fix the environment. Run again
only the reports it touched on the same candidate, and note it in their fiches.

## 6. Where the proof goes

1. The five fiches stay in `output/freeze-and-use/<digest>/` (private).
2. Before the tag, post a comment on the release pull request with the public
   part of the record (section 4): the candidate digest, the five dates, the
   aggregates, and the incidents with their classes. This follows
   [readiness, How to use](1.0-readiness.md#how-to-use-it), step 2.
3. Fill the gate in the readiness record:
   `freeze_and_use: {status: pass, evidence: <URL of the comment>}`, or `fail`
   with the evidence of the blocking incident.
4. Commit the filled gate into [1.0-readiness.md](1.0-readiness.md) in the next
   pull request, as step 3 of its *How to use* says. That commit does not change
   the candidate.

## 7. Open before the freeze

The protocol needs these, and the repository does not have them yet. Each
must be done or decided before the first import.

1. **The checks of step 7 on an arbitrary bundle: written, not yet run on the
   stack.** `scripts/opencti_import_bundle.py` runs them (TESTING.md, *Any
   bundle*, issue #708), and its tests run them on a fake client. A run on the
   throwaway OpenCTI of `docker/opencti-test` is still to be done and recorded
   before the freeze. Until then, nothing in this section is proof for the five
   reports.
2. **The provider of the run.** The maintainer chooses the `LLM_PROVIDER` and the
   model before the freeze, and writes them in the readiness record
   (`configuration.model_and_corpus_revisions`). The default provider has its
   own gate, `default_provider_measured` (ADR-0094 item 11). This protocol does
   not choose it, and each fiche records the one used.
3. **The cutoff date and the five picks,** written in the private log before the
   first import (section 2).
