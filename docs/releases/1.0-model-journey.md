# 1.0 model journey

ADR-0097 item 24: a report goes through the whole pipeline on a running stack,
with the real models and the configured LLM, once as a PDF upload and once as a
captured URL. The script is `scripts/check_model_journey.py`. It is a
qualification step, run on the candidate.

The offline browser journey (`scripts/check_browser_e2e.sh`) and the Docker smoke
(`scripts/docker_smoke.sh --job`) do not cover this. The offline journey runs
without the models. The smoke uploads a text and reads the stage report. Neither
imports a PDF or a URL with the models and the LLM.

The script is not in CI. It needs a stack with the models loaded, a reachable
LLM, and network access for the URL. Its tests (`tests/test_model_journey.py`)
run in CI and need no Docker.

## What it proves, and what it does not

It proves that, on the stack it is run against:

- a PDF uploaded through `POST /api/upload` and a URL captured through
  `POST /api/ingest/url` each end `completed` or `for_review`;
- the stages named in `--required-stages` ran, Stage 3 included, with its egress
  record allowing the report and at least one provider call;
- the models ran (stages 2c and 2e are in the report as `ran`; 2d is off by default);
- the document text was read, and something was extracted (an entity, and an
  IoC or a technique);
- the bundle exports as a STIX 2.1 bundle with a `report` object and no
  relationship that points at a missing object;
- for the URL, the captured source is recorded and its archive is served.

It does not prove the quality of the extraction. A run that finds one entity
passes check 5. The precision and recall of the models are measured by the
evaluation (`docs/eval/`), not here. It does not check the content of the bundle
against the report, nor the review in the UI. It runs two jobs, one after the
other: it is not a load test.

## Prerequisites

- A stack from the candidate, started as [docker.md](../docker.md) describes,
  with `bootstrap` done, so that the API answers `GET /api/health` with 200.
- The models loaded: the 2c and 2e stages must not be skipped (2d is off by default, ADR-0099). The stack
  must not set `SKIP_HEAVY_MODELS`, `GLINER_ENABLED` must be true and
  `GLINER_ENTITY_TYPES` must name a type (ADR-0098), or check 3 fails.
- A reachable LLM for Stage 3 (`LLM_PROVIDER` and its endpoint). The script
  reads the provider and host from `GET /api/llm/egress` and records them. It
  does not read the model: no route reports it, so the report says "not
  reported".
- Network access from the stack to the URL. A capture that the route filter
  refuses, or a page that does not render, fails check 0 or check 7.
- The script runs from WSL or a Linux shell. It uses the standard library only.
- Nothing else uses the queue. The journey waits for its two jobs.

## The command

```bash
python3 scripts/check_model_journey.py \
    --pdf path/to/report.pdf \
    --url https://example.org/report
```

Options:

- `--base-url` (default `http://127.0.0.1:8000`). It must be on loopback. Any
  other host exits 2 before a request.
- `--pdf PATH` (required). The file must exist and start with `%PDF-`.
- `--url URL` (required). An `http` or `https` URL with a host.
- `--report-dir` (default `output/model-journey/<UTC time>`).
- `--wait-s` (default 2400). How long each job may take to leave `uploaded`,
  `queued` and `processing`.
- `--required-stages` (default `2c 2e 3`). Stages that must be `ran`.

For a stack with authentication, export `CTIPARSOR_TOKEN` with a token. The
script sends it as a bearer. It is never written to the report.

The script exits 2 for a usage error, before any request: a bad URL, a missing or
non-PDF file, a base URL off loopback, a bad `--required-stages`. It also exits 2
when `/api/health` does not answer 200, since no job has been submitted then.
Exit 0 means every check of both journeys passed. Exit 1 means one did not.

## The checks

Each journey has these checks. Each has a status, `pass`, `fail` or
`not_checked`, and a detail.

| Check | Passes when |
|---|---|
| 0 job created | The POST answers 200, 201 or 202 with a job id. |
| 1 job ended | The job ends `completed` or `for_review`. A job still `uploaded`, `queued` or `processing` at `--wait-s` fails it. |
| 2 required stages ran | Each stage of `--required-stages` is `ran` in the stage report. Stage 3 also needs an egress record with `allowed` true, and `provider_calls` above zero. |
| 3 models ran | Stages 2c and 2e are in the report and `ran`. Any skip fails it, whatever the reason. |
| 4 document text | Stage 1 records more than zero characters. The report does not record pages. |
| 5 extraction | The job has at least one entity, and at least one IoC (`ipv4`, `ipv6`, `domain`, `url`, `email`, `md5`, `sha1`, `sha256`) or technique (`ttp`). |
| 6 bundle exports | `GET /api/jobs/{id}/bundle` answers 200 with `type: bundle`, objects, a `report` object, and relationships whose `source_ref` and `target_ref` are objects of the bundle. |
| 7 captured source recorded | URL journey only. The POST answers a final URL, and `GET /api/jobs/{id}/source` answers 200 with the archive. |

The stages come from the job's stage report (`stages` of `GET /api/jobs/{id}`).
A skip has the reason the pipeline wrote. Stage 2e is skipped with the
reason "model or index unavailable" when the model is off or not installed, and
that reason does not name `SKIP_HEAVY_MODELS`. Stage 2d is skipped with
"disabled: CYNER_ENABLED is not true" unless it is turned on. Stage 2e is skipped with
"disabled: GLINER_ENTITY_TYPES names no entity type" when no type is named,
and is `failed` when its model did not load or answered nothing (ADR-0098).
Read the stage's entry in the report to see what happened.

The report also records, per journey, the job id, the times and the stage
durations. The times are what the script observed at its polls (`posted`,
`started`, `ended`), and the server's `created_at` and `updated_at`. A job that
ends between two polls has no observed `started`. The durations of the stages
are the ones the stage records give.

## The reports

The run writes `report.md` for people and `report.json` for scripts into the
report directory. Both hold the server facts (the API version, the LLM provider
and host, and "not reported" for what no route gives), then per journey the
input, the checks, the times, the stage durations and the bundle's sha256 and
object counts. The URL is written without its credentials and its query. No
token is written.

## How to read a failure

| Failing check | First look at | Then |
|---|---|---|
| 0 job created | The POST status and body in the detail | 413 or 415: the file. 429: the rate limit (10 uploads or 5 captures a minute). 503: the queue is full. 502, 503 or 504 on the URL: the capture, its detail names the cause. |
| 1 job ended `failed` | The job's stage report: the stage marked `failed` and its reason | The worker's log (`docker compose logs worker`) for that job id. |
| 1 job not ended | The queue (`GET /api/queue/status`): a worker that runs, a queue that moves | Raise `--wait-s` only when the queue moves. |
| 2 stage skipped or missing | The stage's reason | A reason that names the endpoint or the connection is the LLM. `LLM provider not ready` is the configuration. |
| 2 stage 3 refused by egress | The `egress` record and the report's TLP | The report's marking, or `LLM_PROVIDER`. See [api.md](../api.md#llm-egress-adr-0097). |
| 3 model skipped | The reason of the model stage | `GLINER_ENABLED`, `CYNER_ENABLED`, `SKIP_HEAVY_MODELS`, and the model files in the image. |
| 4 no text | The file, and the stage 1 record | A scanned PDF with no text layer, or an empty capture. |
| 5 no entity, or no IoC or technique | The stage 2 and 3 counts | A short or unusual report. Record it, and do not change the check. |
| 6 bundle answers 409 | The detail of the 409: the validation errors | Stage 5 refused the bundle. See [api.md](../api.md#a-bundle-stage-5-refuses-adr-0084). |
| 6 relationship to a missing object | The detail names the relationship and the reference | A bundle that does not hold what it links: a stage 4 defect. Stop, and report it with the run directory. |
| 7 source not served | The archive file under `uploads/` | The capture wrote the text and not the archive. |

A run that fails leaves its jobs in the stack. Their ids are in the report, so
the jobs can be read in the UI or with `GET /api/jobs/{id}`.
