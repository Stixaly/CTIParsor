# 1.0 readiness checklist

The checklist the 1.0 release is decided on: for each gate, what shows it, how
to run it again on the candidate, the evidence so far and what is still open.
The promises are in [support-policy.md](../support-policy.md); the decision and
the work items are in [ADR-0094](../adr/0094-what-1-0-promises.md), accepted
on 2026-11-01.

**No candidate is frozen (2026-11-01).** Every gate in the record below is
`not_run` and every value `null`. The *Evidence so far* column says what
exists on `main`, not what has been shown on a candidate. 1.0 is released when
the blocking gates are shown, not because a date arrives.

## How to use it

1. **The candidate** is the merge commit of the release pull request and the
   image main's CI published for it
   ([releasing.md](../releasing.md#cutting-a-release), steps 4 and 5).
2. **Run each gate again on that candidate** (column *Re-run on the candidate*),
   or carry its evidence over and write why it still holds, and post each
   report on the release pull request, as step 4 of releasing.md does.
   Evidence is renewed when what it assumed changes: the code, the image, the
   configuration, a model, a corpus, the contract, the consumer (OpenCTI).
3. **Fill the record**: each status, with `evidence` pointing at the run or the
   report posted. Post the filled record on the release pull request before
   the tag; commit it into this page in the next pull request. That later
   commit does not change the candidate: the tag names the release's merge
   commit.
4. The maintainer fills `approval`. `decision` stays `pending` until then.

The rules:

- The statuses are `pass`, `fail`, `not_run` and `not_applicable`.
- A blocking gate (`gates`) that is not `pass` stops the release.
  `not_applicable` cites the scope that excludes the gate, and is not a success.
- A reinforcement (`reinforcements`) may stay `not_run`. The release notes say
  whether it was done.
- This page holds aggregates that can be published. The in-house corpus
  manifest is private: `private_manifest_reference` names where it is kept,
  never its content.

```yaml
  double_annotation: {status: not_run, evidence: null}
  external_install: {status: not_run, evidence: null}
  analyst_pilot: {status: not_run, evidence: null}

  maintainer: null
  date: null

```

What fills the values:

- `git_commit`: the merge commit of the release pull request, which the tag
  names ([releasing.md](../releasing.md#cutting-a-release), step 5).
- `image_digest`: the digest of `ghcr.io/stixaly/ctiparsor:sha-<commit>`, the
  one `container-image` tested and `publish-image` read back
  ([below](#the-published-image-is-the-one-that-was-tested)).
- `contract_revision`: the revision of the `contract/` snapshot that
  `scripts/contract.py check` passed against on that commit.
- `public_fingerprint`, `model_and_corpus_revisions`: the configuration and the
  data of the published measurement (gates `quality_published` and
  `default_provider_measured`): commit, image digest, LLM provider and model,
  sampling (`LLM_TEMPERATURE`, `LLM_SEED`), ATT&CK release
  ([support-policy.md](../support-policy.md#quality-what-is-measured-and-published)).
  Both stay `null` while no measurement exists.
- `private_manifest_reference`: where the in-house manifest is kept
  (ADR-0094 item 5). It is `data/eval/inhouse/manifest.json`, git-ignored,
  written on 2026-11-08 (sha256 `c78981a8af596cb29bae8f7bd7b6e61e6fd2c05f6090e777713f4c1251ef5957`).
  For each of the 8 gold reports it records:
  - the source file's sha256, size, format and pages;
  - the gold.json's sha256, layers, guide version and counts per layer;
  - the language, the family (the two GREYVIBE reports are one), the sharing
    rights and the partition.

  It also records how the set was annotated and the removed report. The
  record names this path and that sha256; a gold or source change gives
  another sha256.

   [ADR-0078](../adr/0078-repository-security-settings-and-workflow-hardening.md)
   said 13 until 2026-11-08; both now say 14 (the count in the ADR is dated
   2026-10-10 and kept as written there).

### Tag protection

The API lists one ruleset: id 19765507, "basic rules", target branch. **No
ruleset covers `v*` tags** (2026-11-01). Without one, anyone with write access
can create, move or delete a release tag, and the release workflow's checks
stop a mistake, not a person
([releasing.md](../releasing.md#what-the-workflows-checks-are-worth)). The
settings and the clicks are in
[releasing.md, One-time repository settings](../releasing.md#one-time-repository-settings),
item 1; ADR-0085 action item 2 is open. Read back:

```bash
gh api repos/Stixaly/CTIParsor/rulesets --jq '.[] | [.id, .name, .target, .enforcement] | @tsv'
```

### The published image is the one that was tested

`container-image` builds the image once, scans and smoke-tests it. On `main`,
`publish-image` pushes that build's OCI archive without a rebuild, and fails
unless the registry holds the digest `container-image` reported
([releasing.md, The image main's CI publishes](../releasing.md#the-image-mains-ci-publishes),
[ADR-0047](../adr/0047-publish-image-to-ghcr.md)).

**Read on 2026-11-08, for the release 0.6.0 commit `45aa96cffec23e26134887cb39132a81a8ec91b1`
(CI run `42470778393`, every job `success` but the skipped dependency review):**

- `container-image` logged `image index: sha256:7183e35d13b77c3a34af548e23fa768b4fe8be19fa2e81476e358a336c9b0df4`;
  `publish-image` printed `sha-45aa96c…` and `latest` as that same digest; GHCR
  served that digest for `sha-45aa96c…` and for `0.6.0` on 2026-11-08. These
  three values are one.
- The loaded image's ID logged by `container-image` is that index digest: the
  step "Load the archive as ctiparsor:ci" printed `ctiparsor:ci, loaded: image ID sha256:7183e35d…`.

- The raw index (`docker buildx imagetools inspect … --raw`) holds two
  manifests: the linux/amd64 image `sha256:ebeb76e5…` and an
  `attestation-manifest` (`sha256:6327dc62…`) that references it.
- `gh attestation verify oci://ghcr.io/stixaly/ctiparsor@sha256:7183e35d…
  --signer-workflow Stixaly/CTIParsor/.github/workflows/ci.yml --source-ref
  refs/heads/main --source-digest 45aa96c…` passes for the SLSA provenance
  (`https://slsa.dev/provenance/v1`) and, with `--predicate-type
  https://cyclonedx.org/bom`, for the SBOM; both are signed by `ci.yml` on
  `refs/heads/main` at that commit.

`latest` is not compared here: it moves with each push to `main`.

The commands below remain the way to read the next release's run, read-only,
with the commands of the releasing.md section:

- the image index `container-image` logged, both digests `publish-image`
  printed (`sha-<commit>` and `latest`) and the digest GHCR serves for
  `sha-<commit>` are one value;
- the loaded image's ID is that index digest: both jobs require the
  containerd image store and fail, naming the store, on any other;
- the raw index holds two manifests, linux/amd64 and an `attestation-manifest`;
- `gh attestation verify` passes with `--source-digest <commit>`.

Only that run shows GHCR accepting the index `docker push` sends from the
containerd store, attestation manifest included, the 1 GB artifact `ctiparsor-image` surviving its upload and download, and the
runner's disk. If `publish-image` fails after its push, `sha-<commit>` may be
on GHCR unattested, which a release refuses, and `latest` still names the last
tested digest. Re-run the failed job within a day, the artifact's retention.
Record what was seen in ADR-0047's amendment.
