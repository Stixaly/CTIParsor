# ADR-0079: Python 3.14 for the image and CI

**Status:** Accepted
**Date:** 2026-10-04
**Deciders:** maintainer
**Amends:** ADR-0044 (container images), ADR-0075 (supply chain)

## Context

The first Grype scan of the image (ADR-0078) reported seven vulnerabilities
in Python 3.12.15 that are fixed only in Python 3.13 and later, not
backported to 3.12:

- base64 decoding (two);
- imaplib and poplib command injection;
- the `tempfile.TemporaryDirectory` cleanup race;
- `http.cookies` `js_output`;
- `pkgutil.get_data` (disputed).

None is reachable from CTIParsor; the only use of these modules is
`TemporaryDirectory` in a measurement script. 3.12 is in security-only
maintenance, though, and fixes like these will keep landing on newer
branches only. The maintainer's development venv has run Python 3.14 since
2026-09-08, with the full fast suite passing.

## Decision

The image, CI and the lock move to **Python 3.14**:

- `python:3.14-slim-bookworm` (3.14.8), pinned by digest;
- `setup-python` 3.14 in the three CI jobs that install Python;
- `make lock` / `make audit` on 3.14, and the lock re-resolved with
  `--python-version 3.14`.

What 3.14 needed:

1. **onnxruntime 1.20.1 → 1.30.0** (via magika, the upload type check):
   1.20.1 has no 3.14 wheel and no sdist, so it cannot install. magika stays
   0.6.3 on Linux. 0.6.3 caps onnxruntime at 1.20.1 on Windows only, so the
   universal lock gives Windows magika 0.6.2. coloredlogs, humanfriendly and
   pyreadline3 drop out with the old onnxruntime.
2. **yara-python is compiled.** 4.5.4, the latest release, publishes no 3.14
   wheel, so pip builds it from the sdist in the builder stage. **The builder
   now installs `libssl-dev`**: without the OpenSSL headers the build
   succeeds but leaves out the `hash` module and PE signature parsing, with
   no error. The Stage 4 YARA gate (ADR-0067) would then refuse rules
   OpenCTI accepts. `tests/test_yara_check.py` now asserts those modules are
   there, so CI and the image's test run catch a regression. It already
   caught one: the maintainer's local 3.14 venv, built without
   `libssl-dev`, has had no `hash` module since its move.

Every other compiled dependency of the 159 pins publishes a cp314 or abi3
wheel, 42 packages in all, among them torch, numpy, scipy, spacy,
google-re2, pyahocorasick, psycopg and onnxruntime (checked against PyPI and
the PyTorch CPU index). `cpe` has no wheel for any Python and installs
from its pure-Python sdist, as before.

## Consequences

- **Fixed:** Python 3.14.8 fixes five of the seven Grype findings. Two are
  fixed only in 3.15: poplib command injection and the `TemporaryDirectory`
  race. They are not reachable from CTIParsor.
- **Harder:** yara-python is built, not downloaded, until a 3.14 wheel
  appears. That adds about 10 s to the builder stage, and depends on
  `libssl-dev` staying in it.
- **To revisit:**
  - a published yara-python 3.14 wheel, after which the source build can go;
  - Debian 13 (`-slim-trixie`). Debian 12 left regular security support in
    June 2026 and is now under LTS. This ADR keeps bookworm so the Python
    change is tested alone.
